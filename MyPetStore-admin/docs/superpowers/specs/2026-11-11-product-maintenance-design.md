# 后台商品维护与补货设计

## 意图

完成 PRD `FR-A-03` 与 `FR-A-04` 的管理端闭环。管理员能够创建默认下架的商品、维护商品资料、显式上下架，并以增量方式补货；所有写操作都遵守商品版本，避免覆盖用户端购买、取消或另一管理员刚刚产生的数据变化。

## 目标

- 商品列表增加一级分类、二级分类、名称、状态筛选，并展示排序和操作入口。
- 新增商品时校验 SKU、二级分类、名称、价格、初始库存、简介、描述、封面路径和排序；状态固定为 `DRAFT`、版本固定为 0。
- 编辑时允许修改分类、名称、价格、简介、描述、封面路径和排序；SKU 与库存只读。
- 提供独立的上架、下架和增量补货操作。
- 商品资料编辑和上下架使用提交时携带的旧 `version` 做乐观锁更新；补货直接在数据库最新库存上原子增加。所有成功写入均递增版本。
- 数据库约束竞争、非法参数和不存在记录均转换为可理解的业务错误，不展示 SQL 或堆栈。

## 非目标

- 不删除商品；下架是停止新销售的唯一管理操作。
- 不实现图片上传、相册维护、富文本、销量统计、多规格或直接设置绝对库存。
- 不在本阶段实现用户端商品详情与购买，也不伪造跨应用并发验收结果。
- 不修改课程数据库结构和既有演示数据。

## 约束与业务规则

- SKU 去首尾空白，长度 1—40，全局唯一，创建后不可变。
- 名称去首尾空白，长度 1—120；简介可空且最长 500；描述为可空纯文本。
- 商品必须归属存在的二级分类，一级分类只能用于筛选和表单分组。
- 价格大于 0、最多两位小数且不超过 `DECIMAL(12,2)`；库存和排序为非负整数。
- 封面路径去首尾空白、长度 1—255，只接受站内相对资源路径：不能是绝对路径、URL，不能包含 `..`，统一默认值为 `images/logo.png`。
- 新增商品始终为 `DRAFT`；库存为 0 仍允许上架，用户端应显示售罄。
- 编辑和状态表单携带隐藏版本，但服务端只把它当作旧版本条件；补货表单只提交增加数量；新版本永远由 SQL `version = version + 1` 产生。
- 补货数量必须是正整数，且 `stock + quantity` 不得超过 Java/MySQL `INT` 上限；SQL 在数据库当前库存基础上原子增加。
- 所有写请求为 POST，并沿用现有 Spring Security 的管理员认证和 CSRF 防护。

## 方案比较

1. 分两次实现：先新增编辑，再上下架补货。单次改动较小，但中间状态无法通过 `FR-A-03/04` 验收，版本策略也容易重复返工。
2. 完整纵向闭环：一次完成模型、Mapper、Service、Controller、页面和测试。改动较大，但所有商品写操作可以共享同一套校验与乐观锁语义。采用此方案。
3. 使用 MyBatis-Plus 通用 `updateById`：代码较短，但容易把旧库存或客户端版本一起写回，无法清楚证明资料编辑不覆盖并发库存。拒绝该方案，使用显式 SQL。

## 分层设计

### 模型

扩充 `Product` 为完整表字段。增加商品创建命令、资料更新命令、补货命令、编辑视图及二级分类选项 DTO。表单命令只表达允许输入的字段，避免直接绑定持久化实体。

### Mapper

- 列表查询联接二级和一级分类，并支持一级分类 ID、二级分类 ID、名称或 SKU 关键字、状态及固定每页 10 条分页。
- 查询商品详情、SKU 冲突和二级分类归属。
- 创建使用显式字段插入，状态和版本由服务端确定。
- 资料更新 SQL 只修改允许字段，并以 `WHERE id = ? AND version = ?` 限定，成功时版本加一，不写 SKU、库存或状态。
- 上下架 SQL 只修改状态并检查版本；补货 SQL 不检查页面旧版本，使用 `stock = stock + ?`、版本加一，并在条件中防止整数溢出。
- 所有更新依据影响行数区分成功、记录消失或版本冲突；必要时重新读取记录给出稳定提示。

### Service

写操作放在事务中。Service 统一做字符串规范化、数值范围、二级分类、SKU 唯一性和封面路径校验；数据库唯一键竞争转换为安全提示。更新影响 0 行时重新读取：不存在返回 404 语义，仍存在返回版本冲突。上架前重新验证数据库中的分类、价格和封面路径。补货返回更新后的实际库存与版本，用于反馈而不是用页面旧库存计算目标值。

### Web

- `GET /admin/products`：筛选与分页列表。
- `GET /admin/products/new`、`POST /admin/products`：新增。
- `GET /admin/products/{id}/edit`、`POST /admin/products/{id}`：编辑资料。
- `POST /admin/products/{id}/status`：显式上架或下架，提交目标状态和旧版本。
- `GET /admin/products/{id}/restock`、`POST /admin/products/{id}/restock`：独立补货表单。

表单校验失败时保留安全输入和分类选项；业务成功后使用重定向与一次性消息，避免刷新重复提交。列表不出现删除按钮。页面显示中文状态、当前库存和版本冲突提示。

## 错误处理

- 非法输入返回 HTTP 400 的原表单并显示字段或业务提示。
- 商品不存在返回统一 404 页面。
- SKU 重复、非法分类、版本冲突、库存溢出返回安全中文提示。
- 未预期异常由现有 500 页面处理，不输出 SQL、数据库约束名或堆栈。

## 测试与验收

- Mapper 契约测试锁定显式 SQL：资料编辑不写 SKU/库存/状态，状态切换与补货都检查版本并递增。
- Service 单元测试覆盖正常新增编辑、全部字段边界、非法一级分类、重复 SKU、版本冲突、上下架、零库存上架、增量补货和溢出。
- MVC 测试覆盖路由、表单回显、CSRF、只读字段、无删除入口和安全错误。
- 全项目 `clean verify` 必须保持通过。
- 真实数据库检查新增默认下架、编辑不改库存、补货按最新值增加、上下架可见性和旧版本拒绝。
- `AC-25` 的两端一致性与 `AC-28` 的跨工程并发证据，等用户端对应功能具备后再用两个实际应用验证；本阶段只提供管理端与数据库层证据，不把单进程测试冒充跨应用验收。

## 完成标准

管理员能够从真实页面完成合法的新增、编辑、上架、下架和补货；非法分类、重复 SKU、越界数值及旧版本不会修改数据；库存只能由新增初始值或独立增量补货改变；现有登录、分类和商品列表功能及测试保持通过。
