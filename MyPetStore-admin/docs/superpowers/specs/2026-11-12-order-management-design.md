# 后台订单查询、详情与发货设计

## 意图

完成 PRD `FR-A-05`、`FR-A-06` 与 `AC-29` 的管理端闭环。管理员能够查询全站订单、查看不可变的成交快照，并且只把已支付订单发货一次；后台不能借此修改金额、明细、支付信息或任意指定订单状态。

## 目标

- 订单列表支持完整订单号、五种订单状态筛选与分页；默认每页 10 条，可在 1—50 条内调整。
- 列表按 `created_at`、`id` 倒序，展示订单号、用户、金额、状态和关键时间。
- 详情展示用户、收货快照、总额、状态时间线及全部商品成交快照。
- 已支付及后续状态显示固定支付方式 `MOCK` 和支付凭证；未支付、已取消订单明确显示未支付。
- 仅 `PAID` 订单展示发货按钮；服务端再次检查状态后执行 `PAID -> SHIPPED`，并写入首次发货时间。
- 重复发货或对其他状态发货不改变任何数据，并返回安全、明确的提示。

## 非目标

- 不创建、支付、取消或完成订单；这些属于用户端交易流程。
- 不录入物流公司、运单号或物流轨迹。
- 不允许编辑订单金额、收货信息、商品明细、支付凭证或自由选择目标状态。
- 不修改订单表结构，也不伪造用户端尚未完成的真实跨应用验收证据。

## 约束与业务规则

- 订单号筛选去首尾空白，允许空值，非空时最长 40 字符并做完整值精确匹配。
- 状态只允许 `PENDING_PAYMENT`、`PAID`、`SHIPPED`、`COMPLETED`、`CANCELLED`；空值或 `ALL` 表示全部。
- 页码缺省为 1，小于 1 的整数归一为 1；格式错误或数值溢出返回参数错误。`pageSize` 缺省为 10，仅接受 1—50，越界、格式错误或溢出返回参数错误。
- 列表和详情读取 `sales_order`、`sales_order_item` 中的快照字段，不回查当前商品名称、价格、封面来覆盖历史。
- 详情中的所属用户从 `store_user` 读取用户名和显示名；订单不存在返回 404。
- 未支付及已取消订单不显示伪造支付渠道；`PAID`、`SHIPPED`、`COMPLETED` 才显示数据库保存的 `MOCK` 与成功凭证。
- 发货使用单条条件更新：`WHERE id = ? AND status = 'PAID'`，同时设置 `status = 'SHIPPED'`、`shipped_at = CURRENT_TIMESTAMP`。这样并发请求只有一个成功，首次时间不会被第二次覆盖。
- 更新影响 0 行时重新读取订单：不存在返回 404；仍为 `SHIPPED` 或 `COMPLETED` 提示已经处理；其他状态提示当前状态不能发货。
- 所有写请求为 POST，并必须经过现有 Spring Security 管理员认证、`AdminAccountStatusFilter` 账号状态复核和 CSRF 防护；Service 再次检查的是订单当前状态。

## 方案比较

1. 先做只读查询、下一轮再做发货：单次改动较小，但无法形成后台履约闭环，也不能完成 `AC-29`。不采用。
2. 查询、详情、发货完整纵向闭环：模型、Mapper、Service、Controller、页面和测试共享同一套状态语义，完成后即可执行管理端验收。采用此方案。
3. 先读取后在 Java 中修改并 `updateById`：实现直观，但两个管理员并发点击时可能重复覆盖 `shipped_at`。不采用，发货使用数据库条件更新。

## 分层设计

### 模型

- 增加 `SalesOrder` 持久化实体，仅用于映射订单表和状态判断。
- 增加列表行、订单详情、订单明细快照 DTO；列表与详情使用专用只读投影，避免把整张表直接暴露给页面。
- 增加 `OrderListQuery`，负责规范化订单号、状态、页码和页大小。
- 状态文本由集中映射提供，模板不自行推断合法状态。

### Mapper

- 分页查询联接 `store_user`，可组合订单号精确匹配和状态筛选，固定按 `created_at DESC, id DESC` 排序。
- 详情查询联接用户表，读取订单、收货、支付及各状态时间字段。
- 明细只读取 `sales_order_item` 的 SKU、名称、封面、单价、数量和小计快照，按 `id ASC` 排序。
- 发货 SQL 只修改状态和首次发货时间，并把旧状态限制为 `PAID`；不触碰金额、库存、支付字段或订单明细。

### Service

- 查询服务规范化并校验筛选条件和页大小，创建 MyBatis-Plus 分页对象并返回列表；超出末页时保留筛选条件，并由页面提供第一页和最后一页入口。
- 详情服务在同一次只读事务中读取订单与明细；订单不存在抛出专用 404 异常。
- 发货服务在事务中执行条件更新。成功后返回；失败时读取当前状态，区分不存在、已处理和非法状态。
- 不对订单快照做任何派生写入，商品后续变化不会影响订单详情。

### Web

- `GET /admin/orders`：订单筛选、分页与列表。
- `GET /admin/orders/{id}`：订单详情。
- `POST /admin/orders/{id}/ship`：确认后发货，并重定向回详情页显示一次性消息。
- 订单列表新增到后台首页导航；详情页仅在 `PAID` 时渲染发货表单。
- 所有金额固定两位小数；时间统一使用后台页面现有的本地格式。

## 错误处理

- 非法订单号、状态、页码返回 HTTP 400 与安全中文提示，不执行放宽后的查询。
- 订单不存在返回统一 404 页面。
- 非 `PAID` 发货不修改数据，回到详情页显示当前状态不能发货或已经处理。
- 未预期异常由现有 500 页面处理，不输出 SQL、数据库约束名或堆栈。

## 测试与验收

- Mapper 契约测试锁定精确订单号、状态组合筛选、倒序、快照查询及条件发货 SQL；失败发货不得修改金额、库存、支付字段或首次发货时间。
- Service 单元测试覆盖查询规范化、五种合法状态、`ALL`、未知状态、`page=0/-1` 归一、页码格式错误或溢出、`pageSize=1/50`、页大小越界、详情不存在、明细快照、成功发货、重复发货和各非法状态。
- MVC 测试覆盖列表、空状态、详情、发货按钮可见性、POST、CSRF、404 和安全错误。
- 全项目 `./mvnw clean verify` 必须通过。
- 真实数据库验收：找到多明细订单，核对用户端数据与快照；修改商品后详情不变；待支付不能发货；已支付只能发货一次且保留首次时间。
- 两端均具备订单流程后，再运行 `AC-29` 的完整跨应用验收；本轮不把模拟数据单元测试表述为真实双端验收。

## 完成标准

管理员可以从真实后台页面筛选订单、查看完整不可编辑的历史快照，并仅对已支付订单成功发货一次；非法参数、缺失订单、重复操作和非已支付状态均不会造成数据变更，现有登录、分类和商品功能保持通过。
