# 管理端两级分类维护设计

## 意图

完成 PRD `FR-A-02` 的 P0 分类管理闭环，为后续商品新增和编辑提供可靠的二级分类数据。管理员可以查看两级分类、新增一级或二级分类、编辑名称与排序，并在不破坏商品及层级关系的前提下删除分类。

## 目标

- `/admin/categories` 按一级分类及其二级分类分组展示层级、编码、名称、父分类、排序和操作。
- 支持新增一级分类与新增二级分类；二级分类只能选择现有一级分类作为父级。
- 支持编辑名称和排序；编码及父子关系创建后不可修改。
- 删除前由页面确认，服务端再次检查：存在子分类或任意商品引用时拒绝删除。
- 后端验证编码、名称、排序、层级及唯一性，不能依赖浏览器字段限制。
- 所有写请求使用 POST 并保留 Spring Security CSRF 防护。
- 使用自动化测试覆盖有效路径和关键拒绝路径。

## 非目标

- 不做第三级分类、拖拽排序、批量操作、分类启停、图标和说明字段。
- 不做级联删除或因删除分类而修改、删除、上下架商品。
- 不在本阶段实现商品新增编辑，也不修改数据库结构和演示数据。
- 不增加 REST API 或前端 JavaScript 框架。

## 约束与业务规则

- `code` 去除 Unicode 首尾空白后必填，最长 32，数据库中全局唯一，创建后不可修改。
- `name` 去除 Unicode 首尾空白后必填，最长 50；同一父级下唯一，不同一级分类下允许同名二级分类。
- `sortOrder` 必须是非负整数。
- 一级分类的 `parentId` 必须为空；二级分类的 `parentId` 必须指向现有一级分类。
- 编辑接口只接受 `name` 和 `sortOrder`。即使请求篡改 `code` 或 `parentId`，服务端也没有相应写入路径。
- 删除一级分类前检查子分类；删除任意分类前检查商品引用。任何一项存在都拒绝。
- 展示顺序为 `sort_order`、`id`；一级与各自二级分类分别按此顺序排列。
- 分类列表以一级分类为分页单位，默认每页 10 个一级分类，并完整带出本页一级分类的二级子树；不为展示一页加载全表。
- 后台允许任意满足两级结构的分类，不凭名称或编码后缀虚构 `PETS/SUPPLIES` 类型约束。后续用户端以不可变 `categoryId` 访问新增分类；`PETS/SUPPLIES` 仅作为种子数据中“宠物/用品”的快捷筛选语义。
- 唯一约束竞争最终由数据库兜底，并转成统一、可理解的表单错误，不能暴露 SQL 信息。

## 方案比较

### 方案一：完整垂直闭环（已选择）

一次实现模型、Mapper、Service、Controller、Thymeleaf 页面和测试。优点是分类模块完成后即可作为商品维护的稳定依赖，直接满足 `FR-A-02`；代价是单次改动比只读列表更大。

### 方案二：先只读列表，再补写操作

每次改动较小，但第一阶段不能验收，且会产生暂时可见但不可维护的半成品页面。用户选择不采用。

## 分层设计

### 模型与查询结果

- `Category` 映射 `category` 表的可写字段，不映射生成列 `parent_key`。
- `CategoryTreeItem` 表示页面需要的一、二级树节点，可包含 `children`，避免模板自行拼接关系；分页结果的总数按一级分类计数。
- `CategoryCreateCommand` 与 `CategoryUpdateCommand` 分离，结构上保证编辑不能修改编码和父级。
- Service 返回明确的业务结果或抛出分类业务异常，Controller 负责将异常转换为表单错误或重定向提示。

### 数据访问

- `CategoryMapper` 继承 MyBatis-Plus `BaseMapper<Category>`。
- 列表先分页读取一级分类，再只查询本页一级分类的全部直接子分类，均按 `sort_order, id` 稳定排序，由 Service 组装为两级树。
- 删除前分别查询直接子分类数量和商品引用数量。
- 唯一性先做可读性检查；数据库唯一索引处理并发竞争。

### 业务服务

- `listTree(query)`：按一级分类分页读取并组装本页完整二级子树；若本页数据出现孤儿或三级异常数据，不静默当成一级，而是拒绝组装并给出内部数据异常。
- `listTopLevelOptions()`：供二级分类表单选择父分类。
- `create(command)`：规范化输入、验证字段和层级、检查唯一性后插入。
- `getForEdit(id)`：返回固定编码、固定父分类及可编辑字段。
- `update(id, command)`：重新读取目标，只更新规范化后的名称和排序，并检查同级重名。
- `delete(id)`：事务中重新读取目标并检查子分类及商品引用，满足条件才删除。数据库外键仍作为最终保护。

### Web 路由与页面

- `GET /admin/categories`：分类树列表。
- `GET /admin/categories/new?parentId=`：新增表单；无 `parentId` 为一级，有值为二级并校验父级。
- `POST /admin/categories`：创建分类。
- `GET /admin/categories/{id}/edit`：编辑表单。
- `POST /admin/categories/{id}`：更新名称和排序。
- `POST /admin/categories/{id}/delete`：受限删除。

新增和编辑共用 `category/form.html`，但编辑时编码和父分类仅显示为只读文字，不提交为可写字段。列表使用内联子行表达两级结构，删除使用带 CSRF 的 POST 表单和浏览器确认。成功操作通过 redirect + flash message 返回列表；验证失败保留用户输入并原页显示字段错误。

列表接受 `page` 参数，规则与统一分页约定一致：缺省或小于 1 时使用 1，格式错误返回 400；每页固定展示 10 个一级分类及其完整子树。

## 错误处理

- 缺失、超长、负排序、非法父级、三级父级：显示确定的中文表单错误。
- 编码重复或同级名称重复：显示统一业务错误，不暴露数据库异常。
- 编辑或删除不存在的分类：返回 404。
- 有子分类或商品引用的删除：拒绝并回到列表显示原因，数据不变。
- 数据库外键或唯一索引竞争：捕获数据完整性异常并映射成安全提示。

## 测试与验收

- Service 单元测试：Unicode 空白、长度、负排序、一级/二级创建、拒绝三级、编码全局唯一、名称同级唯一、编辑不改编码/父级、受限删除。
- Mapper 合约测试：实体不写 `parent_key`，关键查询/排序和引用检查存在。
- Controller/模板测试：列表层级、表单字段、POST 写路由、CSRF、编辑只读字段、删除确认和消息显示。
- 完整执行 `./mvnw clean verify`，并由用户在提供私有 `DB_PASSWORD` 的本机进程中做最终浏览器冒烟。
- “新增二级后用户端可选”以及 `AC-25` 的跨端证据，在用户端工程和后台商品新增具备后统一验证，不阻塞本阶段后台分类闭环的代码完成。

## 完成标准

管理员能在真实数据库中完成合法的两级分类新增、编辑和无引用删除；所有不合法层级、重复值及受引用删除均被后端拒绝；未登录用户不能访问；现有登录与商品列表测试继续通过。
